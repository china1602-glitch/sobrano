# Как устроен Практикум 1.1

## Три части

**Браузер:** HTML задаёт страницы, CSS — оформление, JavaScript — формы, переключение темы и HTTP-запросы. В `web/js/app.js` функция `request()` обращается к API через `fetch`. `showEntry()` создаёт форму дня, обработчик `submit` отправляет введённое. Календарь запрашивает данные месяца у Python; сохранённый день открывается для редактирования. Интерфейс предупреждает о несохранённых изменениях и сохраняет локальный черновик новой задачи или записи.

**Python:** `server.py` принимает HTTP-запрос, проверяет формат и вызывает `Store` из `app/service.py`. Функции `validate_task`, `validate_entry`, `validate_profile` проверяют значения. `calculate_minutes` вычисляет рабочее время; числу часов, присланному браузером, программа не доверяет.

**SQLite:** `Store.connect()` открывает соединение с нужной базой и включает внешние ключи. В таблице `profile` хранится JSON настроек, `tasks` — задачи, `entries` — дневник, `meta` — номер версии данных. SQL-значения передаются параметрами `?`. Изменение проходит внутри транзакции: при ошибке вызывается rollback.

## Пример пути одной записи

1. Пользователь указывает 09:00–17:30, перерыв 60 минут и описание работы.
2. JavaScript отправляет `POST /api/entries?mode=personal` с JSON.
3. `Handler.write()` в `server.py` проверяет тип, размер и адрес запроса, затем вызывает `Store.mutate()`.
4. Python проверяет версию данных, дату, отсутствие второй записи за тот же день и рассчитывает `(17×60+30) − 9×60 − 60 = 450 минут`.
5. SQLite сохраняет запись, номер версии увеличивается.
6. Браузер снова запрашивает `GET /api/state`. Дневник показывает **7 ч 30 мин** фактического времени. При настройке 60 минут это 7,5 часа в зачёт плана, при настройке 45 минут — 10 академических часов. В базе в обоих случаях остаются 450 минут.
7. После перезапуска запись остаётся в `storage/personal.sqlite3`.

## Длительность часа и план

`profile.hour_minutes` содержит 60 или 45. Для старого профиля или резервной копии без этого поля используется 60; прежние записи менять не требуется.

Python вычисляет показатели из сохранённых минут:

- `stats.minutes` — фактические минуты всех записей;
- `stats.hour_minutes` — выбранная длительность часа;
- `stats.credited_hours = stats.minutes / profile.hour_minutes` — часы в зачёт плана;
- `stats.target_minutes = profile.target_hours × profile.hour_minutes` — план в минутах;
- `stats.remaining_minutes` — оставшееся до плана фактическое время, не меньше нуля;
- `stats.progress_percent` — процент выполнения плана. Он может быть больше 100, если записей больше, чем требовалось по плану.

Настройка не изменяет показания часов начала и окончания, перерыв и сохранённые минуты. Это преобразование единицы учёта, а не добавление отработанного времени.

## Календарь

Страница `web/calendar.html` показывает выбранный месяц. Запрос `GET /api/calendar?month=2026-10&mode=personal` возвращает все дни месяца, признаки будущей даты и попадания в период практики, а также итоги за месяц. Дни без записи имеют нулевое время; наличие записи определяется `entry_id`.

Пример ответа по составу данных:

```text
month, today, start_date, end_date, hour_minutes, target_hours, revision
  days[]: date, minutes, entry_id, skill, description, within_period, is_future
  totals: minutes, credited_hours, days
```

В интерфейсе нельзя превращать будущий день в уже отработанное время. Обычные проверки даты, периода и уникальности дня повторяются в Python при сохранении. Описание в API — обычный текст; браузер экранирует его при показе.

## Что открыть перед объяснением

| Что объяснить | Где смотреть |
| --- | --- |
| Запуск и HTTP | `server.py`, `main`, `Handler.get`, `Handler.write` |
| Расчёт часов | `app/service.py`, `calculate_minutes` |
| Даты и время | `validate_entry` |
| Создание и редактирование | `Store.mutate` |
| Структуру таблиц | SQL в `Store.__init__` |
| Статистику и поиск | `Store.state` |
| Пересчёт плана | `profile.hour_minutes` и расчёты `stats` в `app/service.py` |
| Данные календаря | маршрут `/api/calendar` в `server.py`, обработка месяца в `app/service.py` |
| Резервные копии | `backup`, `_restore` |
| Печатный отчёт | `app/reports.py`, `render_report` |
| Форму и запрос | `web/js/app.js`, `showEntry`, `request`, обработчик `submit` |
| Внешний вид | `web/css/style.css`, переменные `:root` и media queries |

`__init__.py` — отметка пакета Python, его небольшой размер нормален. `__pycache__` — автоматически создаваемый двоичный кэш, не учебный исходник.

## Живая демонстрация

Запустите сайт обычной командой и выполните действия самостоятельно:

1. В настройках укажите свои данные, план и длительность часа: 60 или 45 минут.
2. Создайте задачу, измените статус, найдите её поиском.
3. Запишите день 09:00–17:30 с перерывом 60 минут. Покажите рассчитанные 7 ч 30 мин фактического времени.
4. Откройте этот день в календаре: появится существующая запись, её можно дополнить. Вторая отдельная запись за ту же дату не требуется.
5. Сравните учёт 450 минут при часе по 60 и 45 минут: 7,5 часа и 10 академических часов. Верните согласованную для практики настройку.
6. Обновите страницу: сохранённая запись остаётся в SQLite. Начните новую запись, введите текст и проверьте предупреждение перед уходом с формы; незавершённый черновик не влияет на итоги.
7. Выберите период отчёта и откройте печатный дневник.
8. Скачайте резервную копию и объясните разницу между сохранёнными записями в SQLite и локальными черновиками в браузере.

Для просмотра запросов: F12 в браузере → Network → фильтр `api`. Здесь видны настоящие GET и POST. В терминале сервера отображаются те же маршруты и HTTP-статусы.

Для отладки: остановите обычный сервер, поставьте точку останова у расчёта `duration = ...` в `calculate_minutes`, запустите F5. Сохранение дня остановит Python на этой строке. Посмотрите `start`, `end`, `pause`, затем F10 и F5. Настройка `PRAKTIKUM_DEBUG` убирает короткий сетевой тайм-аут на время отладки. В браузере запрос ожидает продолжения выполнения Python.

## Вопросы, в которых стоит разобраться

- Почему нельзя доверять присланному браузером числу часов? Клиент можно изменить; сервер повторяет проверку и расчёт.
- Зачем SQLite? Это настоящее постоянное хранилище без установки отдельного сервера БД.
- Что делает транзакция? Позволяет записать согласованное изменение целиком либо откатить его.
- Зачем версия? Запрос с устаревшим `If-Match` получает 409 и не перезаписывает данные другой вкладки.
- Что происходит при удалении задачи? Дневник сохраняется, внешний ключ становится NULL.
- Почему даты дней уникальны? Чтобы не учесть один рабочий день дважды; существующую запись можно редактировать.
- Где хранятся данные? Сохранённые записи — в `storage/` на компьютере сервера; режимы разделены на две базы. Тема — в localStorage браузера, незавершённые черновики новых форм — в sessionStorage текущей вкладки до её закрытия. Они сохраняются при обновлении страницы.
- Зачем отдельно хранить минуты и часы? Минуты описывают фактическую длительность работы, а 45 или 60 минут на час задают единицу зачёта. Это позволяет изменить единицу без переписывания записей.
- Как безопасно обновить код? Остановить сервер, сделать резервную копию и сохранить прежнюю папку `storage/` рядом с новым `server.py`.
- Работает ли без Интернета? Да, интерфейс, шрифт и картинки локальные. Только внешним ссылкам на документацию нужен Интернет.
- Весь ли проект написан на Python? Нет: сервер и бизнес-логика — Python, интерфейс — HTML/CSS/JavaScript.
- Что можно доработать? Учёт нескольких студентов потребует пользователей, прав доступа и изменения модели данных.

Разберите функции и примеры перед выступлением. Объясняйте решения и фактически выполненную вами работу своими словами, не заучивайте названия без понимания.
