# Сервер «СОБРАНО»: запуск, API и данные

Основной вариант новой версии — **локальный JavaScript API + SQLite**, адрес **http://localhost:8080/**. В нём есть регистрация, вход и сохранённые сборки аккаунта. Для интернета сохранён адаптер Cloudflare Workers/D1. Ранее опубликованная версия была проверена пользователем: сборка сохранялась и открывалась по ссылке. Это не подтверждает размещение более позднего обновления с аккаунтами; актуальный статус — в [ONLINE_CHECKS.md](ONLINE_CHECKS.md).

Python также подходит для настоящего backend. Прежний Python API и отдельная программа Tkinter сохранены; новый сервер использует JavaScript. GitHub хранит код, GitHub Pages исполняет только статические файлы, а не Node.js/Python/SQL API.

## Запуск в VS Code

Установите Node.js 24 LTS или новее. Откройте папку с `package.json`, затем терминал:

```powershell
node --version
node online/server.mjs
```

Откройте **http://localhost:8080/**. Остановка — Ctrl+C. Доступны START.bat, START-ONLINE.bat и конфигурация F5 **«СОБРАНО: онлайн-бэкенд Node.js + SQLite»**. HTTP и SQLite входят в Node.js; для этого запуска npm-пакеты не требуются.

Порт: `node online/server.mjs --port 8081`. Файл базы: `node online/server.mjs --db "C:\Мои проекты\sobrano-data.sqlite"`. Обычный повторный запуск сохраняет записи. Не запускайте два процесса с одной базой для учебной демонстрации.

`localhost` и `127.0.0.1` ведут к своему компьютеру, но для браузера это разные адреса/cookie. Пользуйтесь одним адресом, чтобы вход не казался потерянным. На другом компьютере его `localhost` не открывает ваш сервер.

## Устройство

| Файл | Роль |
| --- | --- |
| `online/server.mjs` | Локальный Node.js HTTP и инициализация SQLite |
| `online/worker.mjs` | Облачный fetch и привязка D1 |
| `online/api.mjs` | HTTP-маршруты, JSON, CSRF, сессия и права |
| `online/domain.mjs` | Серверные каталог, цены, расчёт и строгая проверка |
| `online/auth.mjs` | Проверка пароля и формат хеша |
| `online/store.mjs` | Параметризованные SQL-запросы |
| `online/node-db.mjs` | Локальный `node:sqlite` с интерфейсом D1 |
| `online/schema.sql` | Начальная локальная схема |
| `online/db-schema.mjs`, `drizzle/` | Описание схемы и сгенерированные миграции облака |

Используются стандартные HTTP/Fetch API, без Express. SQL-схема применяется до обработки запросов; пользовательский запрос не создаёт таблицы. Загрузка исходного каталога не должна стирать сохранённые составы.

## Таблицы

- `catalog_entries`: вид строки, исходная позиция, JSON модели/готового состава/предложения.
- `catalog_metadata`: ревизия набора и сведения о фотографиях.
- `visitor_sessions`: гостевые владельцы и сессии; опорные записи владельца сохраняются для связи со сборками.
- `accounts`: UUID, нормализованный логин, отображаемое имя, хеш пароля, владелец, время регистрации.
- `account_sessions`: сессии устройств, хеши токенов, CSRF и срок действия.
- `auth_rate_limits`: серверные счётчики попыток с ограниченным временным окном.
- `saved_builds`: UUID, владелец, название, состав, время, версия и ключ повторной попытки.

Локально база — `instance/sobrano.sqlite`, исключена из Git. В облаке D1 — отдельная база: записи между ними не переносятся автоматически. Исходные JSON находятся в `data/`, сервер загружает их канонические строки в SQL по исходным позициям p0/p1 и далее.

Для резервной копии остановите сервер и сохраните весь каталог `instance/`. Не публикуйте базу с аккаунтами, cookie, `.env` или токены. Миграции, которые уже применены, не переписывают; изменение схемы оформляют новой миграцией.

## HTTP API

| Метод | Адрес | Назначение |
| --- | --- | --- |
| GET | `/runtime.json` | Режим и доступность серверных возможностей |
| GET | `/api/health` | Тип сервера/базы и количество данных |
| GET | `/api/catalog` | Модели, предложения, цены и готовые составы |
| GET | `/api/products` | Серверные поиск, фильтры, сортировка и совместимость |
| GET | `/api/builds` | Готовые сборки по задаче и бюджету |
| POST | `/api/configuration` | Расчёт и проверка состава, без записи |
| GET | `/api/session` | Текущий пользователь/гость и CSRF |
| GET | `/api/auth/me` | Публичные сведения текущего пользователя |
| POST | `/api/auth/register` | Создание аккаунта и вход |
| POST | `/api/auth/login` | Вход в существующий аккаунт |
| POST | `/api/auth/logout` | Отзыв текущей сессии и выход |
| GET | `/api/saved-builds` | Сборки текущего владельца |
| POST | `/api/saved-builds` | Новая запись состава в SQL |
| GET | `/api/saved-builds/:id` | Состав по общей ссылке |
| PUT | `/api/saved-builds/:id` | Изменение своей записи с проверкой версии |
| DELETE | `/api/saved-builds/:id` | Удаление своей записи |

Пустой бюджет означает отсутствие ограничения; 0 — нулевой бюджет. Недопустимое число не превращается в пустой фильтр. Порядок категорий: `cpu,gpu,motherboard,ram,storage,psu,case,cooling`; индекс 0 — реальная модель, не пустое значение.

## Пример расчёта из PowerShell

Сервер остаётся в первом терминале. Во втором:

```powershell
$base = 'http://localhost:8080'
Invoke-RestMethod "$base/api/health"
$r = Invoke-RestMethod -Uri "$base/api/configuration" -Method Post -ContentType 'application/json; charset=utf-8' -Body '{"parts":{"gpu":85}}'
$r.assessments.p40 | ConvertTo-Json -Depth 5
```

p85 — RTX 4090, p40 — БП DeepCool PK550D 550 Вт в текущем каталоге. `allowed: false` показывает применение правила мощности на сервере.

## Пример записи в SQL без личных данных

Ниже создаётся отдельная гостевая учебная запись. Учётные данные не нужно вставлять в исходники. Аккаунт удобнее показать через интерфейс регистрации/входа.

```powershell
$session = Invoke-RestMethod "$base/api/session" -SessionVariable sobranoSession
$headers = @{ 'X-CSRF-Token' = $session.csrfToken }
$body = @{
  name = 'Учебная сборка'
  parts = @{ cpu = 0 }
  requestId = [guid]::NewGuid().ToString()
} | ConvertTo-Json -Depth 4
$saved = Invoke-RestMethod -Uri "$base/api/saved-builds" -Method Post -WebSession $sobranoSession -Headers $headers -ContentType 'application/json; charset=utf-8' -Body $body
$saved | Select-Object id, name, version, canEdit
```

Первый POST возвращает 201. Повтор того же тела в той же сессии — прежнюю запись с 200, без дубля. Та же `requestId` с другим содержимым — 409.

Другой посетитель без авторской cookie может читать:

```powershell
Invoke-RestMethod "$base/api/saved-builds/$($saved.id)" | Select-Object id, name, version, canEdit
```

Он получит `canEdit: false`. Изменение требует сессию владельца и текущую версию:

```powershell
$update = @{
  name = 'Учебная сборка: новая версия'
  parts = @{ cpu = 0 }
  version = $saved.version
} | ConvertTo-Json -Depth 4
$saved = Invoke-RestMethod -Uri "$base/api/saved-builds/$($saved.id)" -Method Put -WebSession $sobranoSession -Headers $headers -ContentType 'application/json; charset=utf-8' -Body $update
$saved | Select-Object id, name, version
```

Повтор старого изменения после успеха — 409. Удалить **только созданную примером запись**:

```powershell
Invoke-RestMethod -Uri "$base/api/saved-builds/$($saved.id)" -Method Delete -WebSession $sobranoSession -Headers $headers
```

## Вход и безопасность

Логин содержит 3–32 латинских буквы, цифры или `_`, сравнивается без учёта регистра. Пароль — 10–128 символов. Отображаемое имя при наличии — до 60 символов. Сервер проверяет эти ограничения независимо от HTML-формы.

Хеш пароля: PBKDF2-SHA256, индивидуальная случайная соль 16 байт, 100 000 итераций, результат 32 байта. Этот параметр позволяет использовать WebCrypto в Cloudflare Workers; не заявляйте его максимальной защитой массового публичного сервиса. Открытые пароли не сохраняются. Вход с неверными данными возвращает общую ошибку; SQL-счётчики ограничивают попытки в 15-минутном окне по логину и клиенту.

Случайный токен сессии хранится в HttpOnly-cookie, в SQL — его SHA-256. Сессия действует 90 дней; на HTTPS cookie имеет Secure, также используется SameSite=Lax. Вход/регистрация меняют токен и CSRF; выход отзывает текущую сессию. Другие устройства имеют свои сессии.

При входе текущие **гостевые** сборки могут перейти аккаунту. Уже принадлежащие другому аккаунту записи не переносятся следующему пользователю того же браузера. Для записей проверяется владелец; запросы изменения требуют CSRF и допустимый Origin. Публичные ответы не отдают хеш пароля, токен, его хеш и внутреннего владельца.

Гостевое сохранение осталось доступным. После потери гостевой cookie его право редактирования не восстанавливается автоматически. В аккаунте можно снова войти паролем к той же базе. Восстановление забытого пароля, подтверждение почты и админка не реализованы. Общая ссылка публична для получателя — не помещайте личные данные в название.

## Ошибки

- Неверные поля/JSON/индексы — 400; неверные или отсутствующие учётные данные — 401.
- Неверный CSRF/Origin — 403. Чужая или неизвестная запись для изменения — 404.
- Устаревшая версия/конфликт ключа повторной отправки — 409.
- Тело больше 64 КБ — 413; неверный Content-Type — 415.
- Известный конфликт компонентов при сохранении — 422.
- Лимит записей владельца или попыток входа — 429, прежние составы не удаляются автоматически.

Частичный состав можно сохранить как черновик. Отсутствующие характеристики аппаратной совместимости не считаются доказательством, что всё подходит.

## Сборка и проверка

```powershell
npm ci
npm run build
node tools/test-javascript.cjs
node tests/browser-smoke.cjs
```

Для полного JS-набора нужны dev-зависимости; основной Node-сервер работает без них. Worker-тестам нужен `dist/`, поэтому сборка выполняется первой. Локальные SQLite/HTTP/Worker-тесты не заменяют проверку реального D1 и публичного адреса. Результаты — [ONLINE_CHECKS.md](ONLINE_CHECKS.md).

Новые миграции генерируются командой `npm run db:generate` при изменении описания схемы. Не правьте уже применённые SQL-файлы. Старый статический интерфейс и Python API честно показывают отсутствие новой серверной авторизации, а не имитируют аккаунт в localStorage.
