# Отбор комплектующих

В локальной версии правила выполняет **`backend/compatibility.py`**: `assess` оценивает кандидата относительно текущего состава, `check` проверяет состав целиком. Интерфейс получает результат через Python API. Фильтрацией товаров занимается `backend/catalog.py`, ценами и бюджетом — `backend/pricing.py`.

На GitHub Pages Python не запускается. Для этого режима сохранены соответствующие клиентские правила в `js/compatibility.js` и `js/core.js`. Каталог и предложения в обоих режимах берутся из `data/catalog.json` и `data/offers.json`. Режим выбирает `js/bootstrap.js` по `runtime.json`; при ошибке API в режиме Python показывается ошибка, а не скрытый клиентский расчёт.

Выбор деталей работает в любом порядке. Например, после выбора GPU с рекомендацией БП от 650 Вт блоки 550 Вт исключаются даже без выбранного процессора. При выборе БП первым исключаются неподходящие видеокарты. DDR5-память ограничивает поддерживающие её платформы ещё до выбора платы.

Кандидат временно заменяет старую деталь своей категории. Посторонний конфликт в другой паре не скрывает подходящий накопитель. Расчёт сам не меняет сохранённый состав пользователя. Сервер проверяет переданные категории и индексы и не принимает произвольный товар только на основании данных из браузера.

## Учитываемые параметры

- CPU и плата: сокет.
- CPU и RAM: поддерживаемые типы памяти.
- Плата и RAM: тип, предельный объём, число слотов и модулей.
- Плата и корпус: поддерживаемый форм-фактор.
- CPU и кулер: заявленные сокеты крепления.
- Кулер и корпус: высота.
- GPU и корпус: длина конкретной платы, если она указана.
- БП и корпус: длина блока.
- CPU, GPU и БП: рекомендация видеокарты и расчёт мощности с запасом.

Полный порог БП равен большему из рекомендации видеокарты и оценки нагрузки, округлённому вверх до 50 Вт. В оценке складываются известная мощность CPU, GPU и 75 Вт на остальные компоненты, затем добавляется 25% запаса. Если у CPU задан TDP, а не максимальная мощность, применяется коэффициент 1,5. Это консервативный ориентир подбора, а не измеренное потребление и не физическая граница работоспособности.

Частичные данные позволяют исключить БП ниже уже известной рекомендации или нижнего порога. Например, мощная видеокарта ограничивает выбор БП до выбора процессора. Неизвестная нагрузка не превращается в ноль. Полный расчёт `need` появляется только при достаточных данных; иначе результат содержит ограничение проверки.

## Состояния проверки

| Состояние полного состава | Значение                                                       |
| ------------------------- | -------------------------------------------------------------- |
| `conflict`                | Найден известный конфликт выбранных деталей                    |
| `incomplete`              | Не хватает обязательных компонентов                            |
| `unknown`                 | Обязательные детали выбраны, но не хватает части характеристик |
| `ok`                      | Заполненные базовые проверки не выявили конфликтов             |

`ok` относится к реализованным правилам и имеющимся данным. Он не подтверждает все аппаратные условия. У кандидата свои состояния: `conflict`, `unknown` или `compatible`; неизвестный параметр сам по себе не запрещает выбор.

## Поведение интерфейса

В конфигураторе известные конфликтные кандидаты скрываются. В каталоге фильтр «Подходят к моей сборке» можно выключить для просмотра всех моделей; добавление заведомо конфликтного товара отключается с объяснением. Неизвестные значения не запрещают выбор. Недостающие характеристики перечисляются в общем результате проверки, без повторяющихся подписей под каждой деталью.

В прежнем сохранённом или переданном по ссылке составе конфликтная выбранная деталь остаётся видна с пометкой. Её можно убрать или заменить; состав не очищается автоматически. После удаления ограничения списков пересчитываются. Узлы полей сохраняются при обновлении, чтобы не терять клавиатурный фокус.

В локальном режиме поиск и сортировка вызывают `GET /api/products`, изменения состава — `POST /api/configuration`. Сервер возвращает итог проверки, бюджет и оценку каждого кандидата с признаком `allowed`; интерфейс использует эти оценки для списка выбора. Посмотреть запросы можно в Network браузера, а исполнение `assess` — точкой останова Python. Шаги — [DEFENSE.md](DEFENSE.md).

## Предел проверки

В каталоге есть несовместимые платформы AM4, AM5 и LGA1700, DDR4 и DDR5. **Любое сочетание товаров из каталога не гарантирует рабочую сборку.**

В предыдущей проверке 22 готовых составов известных конфликтов не найдено: 12 прошли заполненные базовые проверки, для 10 не хватало части характеристик. Это результат правил по имеющимся данным, а не подтверждение BIOS, QVL и физической сборки. При обновлении данных результат следует перепроверять.

Отдельной сверки требуют версия BIOS, QVL, профили памяти, достаточность охлаждения под нагрузкой, разъёмы и кабели питания, комплект креплений, зазоры с радиаторами и накопителями. У 42 из 47 строк GPU в исходном наборе отсутствует длина конкретной платы партнёра. Фотография линейки не является источником размеров конкретного исполнения.

## Автоматические проверки

Из корня проекта:

```powershell
py -m unittest discover -s tests -p "test_*.py" -v
node --test tests/compatibility.test.cjs tests/core.test.cjs
```

Python-команда проверяет серверный движок и HTTP API; Node.js — соответствующие правила статического режима. Выполненные сценарии и ограничения приведены в [QA.md](QA.md).
