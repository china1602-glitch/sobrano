# Как устроено «СОБРАНО»

Основной локальный запуск: `node online/server.mjs`, затем **http://localhost:8080/**. Редактор VS Code хранит и запускает код, но сам не является backend. Backend — работающий процесс Node.js; его данные находятся в SQLite.

## Frontend: что получает браузер

| Файлы | Назначение |
| --- | --- |
| `index.html` | Главная |
| `catalog.html`, `product.html` | Каталог и карточка компонента |
| `builds.html`, `build.html`, `builder.html` | Готовые составы и конфигуратор |
| `compare.html`, `favorites.html` | Сравнение и избранное |
| `account.html`, `about.html` | Вход/кабинет и описание проекта |
| `css/style.css` | Цветовые переменные, темы, размеры, адаптивность и фокус |
| `js/bootstrap.js` | Определяет режим `server`, `python` или `static` |
| `js/backend-client.js` | Fetch-запросы, ошибки, сессия и CSRF |
| `js/app.js` | События форм/кнопок, вывод DOM и состояние страниц |
| `js/core.js`, `catalog-ui.js` | Модели, состав, отбор и сортировка |
| `js/compatibility.js`, `pricing.js` | Правила совместимости и бюджет |
| `js/media.js`, `product-images.js` | Сопоставления фото, подписи и состояние недоступности |

React, Bootstrap и Express не используются. Шрифт Manrope находится в `assets/fonts/`. Структура HTML, CSS-медиазапросы, DOM и Fetch API достаточны для этого сайта.

В статическом режиме расчёт выполняется браузером. В серверных режимах запрос идёт в API. Ошибка API не маскируется незаметным переходом на клиентскую имитацию.

## Backend: где выполняется запрос

| Файл | Роль |
| --- | --- |
| `online/server.mjs` | HTTP-сервер Node.js: открытие SQLite до запросов, API и публичные ресурсы |
| `online/worker.mjs` | Облачная входная точка Workers с привязкой D1 |
| `online/api.mjs` | HTTP-маршруты, JSON, лимиты тела, сессия, CSRF и права |
| `online/domain.mjs` | Каталог, строгая проверка состава, цены и совместимость |
| `online/auth.mjs` | Проверка учётных данных и хеширование пароля |
| `online/store.mjs` | Параметризованные SQL-операции |
| `online/node-db.mjs` | Адаптер встроенного `node:sqlite` |
| `online/schema.sql` | Начальная локальная схема |
| `online/db-schema.mjs`, `drizzle/` | Описание SQL-схемы и сгенерированные миграции |

Один API использует локальный SQL-адаптер или D1. Это не означает, что локальная и облачная базы синхронизированы: они независимы. Обновление кода аккаунтов необходимо отдельно разместить, прежде чем заявлять его работу на прежнем интернет-адресе.

## Цепочка расчёта

1. В конфигураторе пользователь выбирает видеокарту.
2. `app.js` передаёт состав клиенту API. Тот отправляет:

```http
POST /api/configuration
Content-Type: application/json

{"parts":{"gpu":85}}
```

3. `api.mjs` проверяет JSON, его размер и форму запроса; `domain.mjs` проверяет категории и допустимые целые индексы.
4. Расчёт возвращает `parts`, `check`, `budget`, `assessments` для моделей.
5. Интерфейс обновляет сумму и скрывает кандидатов с `allowed: false`.

В текущих данных p85 — RTX 4090, p40 — БП 550 Вт; для этой пары `allowed` равен `false`. Отсутствующая характеристика не превращается в гарантию совместимости.

Этот запрос **не записывает** сборку. Он только проверяет и считает.

## Регистрация и вход

1. Браузер получает гостевую сессию и CSRF через `/api/session`.
2. Форма регистрации отправляет логин и пароль в POST `/api/auth/register`; форма входа — в POST `/api/auth/login`.
3. Сервер проверяет поля. Логин нормализуется к нижнему регистру; он состоит из 3–32 латинских букв, цифр и `_`. Пароль — 10–128 символов.
4. Пароль преобразуется PBKDF2-SHA256: отдельная случайная соль 16 байт, 100 000 итераций, результат 32 байта. Открытый пароль не записывается в SQL. Этот переносимый параметр учитывает ограничение Cloudflare; учебная реализация не заявляет максимальную защиту массового публичного сервиса.
5. При успешном входе сервер меняет токен сессии и CSRF. Cookie имеет HttpOnly/SameSite=Lax, а на HTTPS — Secure. В базе находится хеш токена.
6. GET `/api/auth/me` возвращает публичные сведения текущего аккаунта. Выход POST `/api/auth/logout` отзывает текущую сессию и очищает cookie.

Аккаунт позволяет войти с другого браузера к **тому же серверу** и получить свои сборки. Регистрация в локальной базе не создаёт автоматически аккаунт в облачной базе. Восстановление пароля по почте не реализовано; общих паролей и фиктивного администратора нет.

## Сохранение и права

1. Пользователь нажимает «Сохранить на сервере» и задаёт название.
2. POST `/api/saved-builds` передаёт `name`, `parts`, `requestId` и `X-CSRF-Token`.
3. API проверяет сессию, Origin, CSRF, поля и известные конфликты состава.
4. `store.saveBuild()` выполняет параметризованный SQL. Новая запись возвращает 201. Повтор той же попытки с тем же содержимым возвращает прежнюю запись с 200.
5. Ссылка `builder.html?saved=UUID` получает состав GET-запросом из базы.
6. Для PUT/DELETE сервер проверяет владельца. PUT требует текущую `version`; устаревшая версия даёт 409.

Гостевой режим сохранён. При регистрации/входе переносятся только составы текущего гостя; сборки другого уже вошедшего аккаунта новому пользователю не передаются. Общая ссылка разрешает чтение и собственную копию, а не редактирование оригинала. Отсутствие кнопки — удобство интерфейса; защиту выполняет сервер.

## Хранение

| Хранилище | Данные |
| --- | --- |
| `data/catalog.json`, `data/offers.json` | Исходные модели, готовые составы, датированные предложения |
| `catalog_entries`, `catalog_metadata` | Каталог в SQL, исходные позиции и ревизия |
| `visitor_sessions` | Гостевые владельцы/опорные записи и гостевые сессии |
| `accounts` | Логин, имя, хеш пароля и связь с владельцем |
| `account_sessions` | Сессии устройств: хеши токенов, CSRF и сроки |
| `auth_rate_limits` | Серверные ограничения попыток входа |
| `saved_builds` | Владелец, название, состав, время, версия и ключ повтора |
| localStorage | Избранное, сравнение и несохранённый выбор браузера |
| JSON/TXT Python-программы | Отдельные файлы, выбранные пользователем |

Локальная SQL-база — `instance/sobrano.sqlite`. Повторный запуск/загрузка каталога не должны удалять пользовательские составы. В запросы SQL значения передаются параметрами; строку логина не склеивают с SQL-текстом. Каталог читается из SQL, а фильтры применяются серверным JavaScript; SQL full-text-поиск не заявляется.

## Ошибки и ограничения

Сервер независимо от формы проверяет типы, JSON, индексы, бюджет, название, пароль и версию записи. У запросов лимит 64 КБ. Есть CSRF и проверка происхождения записи; неверные учётные данные не раскрывают, существует ли логин. Частые попытки входа ограничиваются по логину и клиенту. Назначение этих мер объясняйте на конкретных примерах, не обещая абсолютной безопасности.

50 сохранённых составов на владельца, версия записи и ключ повторной отправки помогают избежать переполнения и случайной перезаписи. Частичный состав можно сохранить как черновик, но известный конфликт даёт 422. Не все аппаратные характеристики известны.

## Отдельная программа Python

`desktop_app.py` создаёт класс `SobranoApp`. `choose()` меняет словарь состава; `load_preset()` загружает готовый вариант; `refresh()` обновляет варианты, расчёт и подписи. `open_file()`/`save_file()` используют `backend/configuration_file.py`, `export_text()` формирует TXT.

Цикл в `refresh()` перебирает категории, условие отбирает допустимых кандидатов. JSON позволяет сохранить структурированный состав и прочитать его обратно. TXT предназначен для просмотра, а не восстановления состояния. Этот путь не использует веб-аккаунт.
